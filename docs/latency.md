# 0.3.0：连接与控制延迟

## 定位结论

2026-10-31，原0.2.0用户操作日志从连接来源选择到结束约6–16秒：每次新建BLE连接、预读、固定等待1秒、回读，最后还等待停止通知和断连，多个阶段叠加。早先同机灯控制约4秒、风温约7秒完成。

低延迟测试进一步证明，冷建连本身可耗约9秒；保持60秒仅改善连续操作，超过一分钟又会冷启动。因此0.3.0默认持续保持连接，并在HA启动/集成加载后后台进行一次只读查询预热，不让这段耗时落在通常的手机首次点击上。

这些是HA服务端协调器测量，不含手机网络往返、云端转发、APP渲染；也不是用独立传感器测得的机械动作起始时间。网络慢仍可能增加APP端延迟。

## 可选连接策略

设置 → 设备与服务 → 九牧 ZS800I → 配置：

| 策略 | 行为 |
| --- | --- |
| 持续保持（默认） | 启动后台只读预热，操作后保留当前连接；无周期轮询 |
| 闲置60秒 | 首次操作才连接，操作结束60秒无新请求就释放；设备通知不延长计时 |
| 每次断开 | 每次操作完成就断开，手机小程序更容易接管，但操作延迟较大 |

默认策略会占用设备的BLE连接。厂商小程序要直连时，按面板上的**释放蓝牙连接**；只断开、不发送马桶动作，随后不会主动抢连，下次HA查询/控制才重新连接。保持连接不等于自动重连保证：设备重启、无线掉线或人为释放后，下一次重新建连仍可能较慢。

## 优化细节

- 单实例会话与同一通知订阅复用，查询/控制/释放共用锁，避免并发争抢。
- 19字节控制仍先取本事务的新FA/E9，盖圈还取新EA，不使用磁盘或同连接旧观察替代基准。
- 单字段1F短开关不消费FA/E9，省去无用途的预读。
- 用接收安静窗口和写入间隔取代一律等待1秒：通常需距离最近通知及写入约0.25秒，最多等待1秒后继续；之后仍重新检查占用/工作/运动限制。
- 控制后给固件0.25秒处理时间；若新通知已匹配，就不再多发查询。必要时约每1秒查询一次，保留约9秒回读窗口。
- 匹配后立即发布真实状态，不等待日后断连；后台通知合并发布，持久化延迟合并，避免逐包刷盘。
- 每个动作仍只下发一次。写入异常存在效果未知窗口，报告未确认，不自动重放；断连失败保留旧client，确认释放前不创建第二连接。
- 启动预热只使用固定E2查询，绝不恢复/重播上次动作；卸载和HA停止会取消预热、清理会话。

`write_ms`是开始调用BLE写入的时间，不是机械启动证明；`total_ms`到控制结果判定，不包含随后持久化和完整手机往返。confirmed只表示写后新观察与目标匹配，不证明命令因果，也不表示清洗等完整流程已经结束。盖圈/冲水/清洗的机械耗时不从灯或温度数据外推。

一次早期零间隔原型在连续写时没有成功恢复灯状态，虽调用写入仅3ms，却回读不匹配；因此没有采用“越快发越好”方案，加入安静窗口和处理间隔后才通过验收。该原型未发布。最终已确认恢复原风温2、灯开启，临时测试自动化配置已删除；最终重启还核对了后台只读预热、39个中文实体、面板引用和部署文件与ZIP一致。

## 观察数据

实体属性提供：

- `bluetooth_connected`：当前跟踪连接状态。
- `last_connection_reused`：最近一次通信是否复用会话，查询也会更新。
- `last_control_write_ms` / `last_control_write_complete_ms`：最近控制开始/完成传输写入的服务端耗时。
- `last_control_total_ms`：最近控制至判定结果的服务端耗时。
- `observed_at`：档位控件对应字段的真实观察时间。

使用APP时优先核对面板显示“已连接”。若服务端已很快而APP仍明显卡顿，再对比同一手机打开HA局域网地址与远程地址的体验，以区分APP网络路径；本次没有假定或更改手机连接配置。
